User guide

User guide#

Learn how to install Twine, run your first workflow, and work with coding agents in your folders.

Install#

Twine requires macOS 26+ on Apple Silicon.

Install it with Homebrew:

brew install --cask twineproject/tap/twine-app

Then open Twine from Applications.

To install manually instead, download the .dmg from the latest release, open it, and drag Twine onto the Applications folder in the disk image. Wait for the copy to finish, eject the Twine disk image in Finder, and open Twine from Applications.

Releases are Developer ID signed and notarized. The license is included inside the installed app bundle.

To update a Homebrew install, quit Twine and run brew upgrade --cask twine-app. To update a manual install, quit Twine, open the new DMG, and drag Twine into Applications, choosing Replace when Finder asks. Your saved work and settings are retained.

Run your first workflow#

  1. Open Twine and choose Open Folder… (⌘O) to select the folder you want to work in.
  2. Create a session to keep the workflows for your task together.
  3. Add a workflow in a new tab (⌘T). Choose Terminal for a shell, or Single agent to work with a coding agent. For an agent workflow, install and authenticate its harness separately, then select it in Twine's launch form.
  4. Start the workflow and enter your command or task in its terminal.

You can return to the session later to review its output or continue working. The sections below explain how to use more workflows and organize your work.

Folder windows#

Open Folder… (⌘O) reuses an empty window or opens another window when a folder is already open. New Window (⌘N) opens a start page. Opening a folder that is already open focuses its existing window, including when opened through a symlink.

Each window has independent sessions, terminals, file tabs, and navigation. Menu commands act on the focused window. Settings, recent folders, and custom workflow types are shared. Closing a window stops only its folder's processes; Close Folder returns that window to the start page. Quitting stops every window's processes and restores all open folders on the next launch. Unavailable folders show an explanation and can be closed without reopening them next time.

Use View → Zoom In (⌘+), Zoom Out (⌘−), and Actual Size (⌘0) to scale the interface from 50% to 200%. Zoom applies to every window, including terminals, editors, previews, and dialogs, and is remembered between launches.

Files#

The sidebar starts open. Toggle it with the toolbar button or ⌃⌘S to browse the folder or make more room for terminals. Expanding a directory loads only its children; empty directories remain visible. Twine refreshes expanded directories and the selected file when they change, including changes made by shells and agents.

Select a file to make small edits to UTF-8 text up to 2 MiB. Use ⌘Z to undo, ⇧⌘Z to redo, and ⌘L to go to a line. Edits save automatically after a short typing pause, including in background tabs. You can keep typing during saves or press ⌘S to save immediately. Unsaved changes show “Edited” in the header. Settings still require an explicit Save. Before saving, Twine checks whether the file on disk has changed. If it has, choose Reload to discard your edits or Overwrite to save them; Cancel keeps the edits without changing the file. Autosave pauses after a conflict or save failure. Use Save or ⌘S to retry; successful saving or reloading resumes autosave. Disk updates refresh clean files and never replace unsaved edits. ⌘W closes the file and returns to the workflow. Binary files, larger files, deleted paths, symbolic links, and special files show an explanatory state. Up to 256 directories can be expanded at once.

The native editor automatically highlights HTML, CSS, Swift, Rust, Python, C, C++, C#, Go, Java, Ruby, JSON, JavaScript/JSX, TypeScript/TSX, TOML, YAML, and shell files. HTML and Markdown files open in Preview; switch to Source to edit with highlighting. Markdown previews follow local links. It detects languages from filenames and script shebangs. Use the language menu in the file header to choose a language, restore Automatic detection, or select Plain Text. The choice stays with that open file tab and never changes the saved text. Colors update as you type and follow the system appearance. Unknown languages and files that exceed the highlighting work budget remain editable as plain text. Shell highlighting uses the Bash grammar; embedded languages in HTML <script>/<style> blocks, strings, or Markdown code fences are not highlighted separately.

Agent workflows#

Choose Adversarial, Coordinator, or a stored custom workflow type from a new tab. Pick a harness for each role instance, and optionally its model and effort level, then start it. Supported harnesses are Codex, Claude Code, pi, Antigravity (agy), OMP (omp), and OpenCode (opencode), installed on your shell's PATH. Choose a model and effort level from the options shown in the launch form. Claude Code also accepts a model name you type yourself. Where available, YOLO lets the harness run without asking for permission before each action. Pi does not ask for permission, so it has no YOLO option. The first stage's agent asks for the task in its terminal and reports it when it finishes, so later roles receive it. Harnesses run directly in the open folder; parallel workers receive their own sub-task and advisory file ownership. Each role has a terminal subtab. Later stages and review rounds reuse a role's live harness conversation when it remains available. After a role completes its assignment, its terminal stays interactive for follow-up prompts. A follow-up to a first-stage agent can start another workflow cycle while retaining the agents and trace history. After a workflow completes or reaches its review limit, turn on Individual mode in the terminal toolbar to follow up with each agent without starting another cycle. Restored workflows resume recorded harness conversations when all unfinished active agents have compatible session handles.

Choose Create your own (⌥⌘N) in a new tab to design a workflow type. Add roles and instructions, order stages and their parallel roles, connect handoffs, and bound review loops. The designer shows validation errors beside each affected element and enables Save only after the current design validates. Use Tab and Shift-Tab to navigate controls, Return to save, and Escape to cancel. The Preview tab shows the graph.

From a type's launch form, Edit workflow type or Edit a copy (⇧⌘E) opens the designer. Saving a built-in creates a custom copy. Editing a custom type adds a version; workflows already started keep their original version. Saved types appear in the catalog and survive relaunch.

Agents advance stages when they explicitly report completion. Terminal text and process exits do not advance a workflow.

Mark done… is always available for an unfinished active role, including after its process exits. Its form also supports review decisions and worker assignments. Review loops stop at the type's limit; Cancel workflow stops all its agents. Runs restored after quitting or a crash resume their unfinished active agents when every one has a recorded harness session. Otherwise they remain interrupted with their saved output. The Traces panel shows each role's stage invocations on compact agent tracks in shared start order, with equal spacing regardless of pauses. Select a step to focus a seven-step window and inspect its stage changes, completions, and handoffs; this history survives reopening the app.

Traces opens in Overview, with steps in start order. Switch to In Depth to inspect the selected step on a timeline of elapsed time: tool calls, parallel subagents, and previews of their inputs and outputs. Search the activity, show only failures, and jump from an activity to its recorded output.

Claude Code, Codex, pi, and OMP can show prompts, tool calls, and responses in Traces. Select a step to jump to its recorded terminal output. Antigravity and OpenCode show workflow activity but do not record individual prompts or tool calls, so In Depth has no detailed activity for them. If detailed tracing is unavailable, you can still use the agent's terminal and review its saved output. Twine leaves your harness configuration files unchanged.

Configuration#

Twine reads $XDG_CONFIG_HOME/twine/config.toml at startup, falling back to ~/.config/twine/config.toml when XDG_CONFIG_HOME is unset, empty, or relative. It creates a commented default config and themes/silica_dark.toml and themes/silica_light.toml beside it on first launch. Existing files are never overwritten.

Choose Twine → Settings… or press ⌘, to edit the config file in a popup attached to the current window. Save with ⌘S or the Save button. Valid settings apply immediately to every open folder; invalid settings keep the previous file and active settings. Unsaved edits are protected when closing the window or quitting, and external file changes prompt you to reload or overwrite.

[appearance]
color_scheme = "system" # "system", "light", or "dark"

[terminal]
font_family = "JetBrains Mono"
font_size = 13.0

Terminal settings apply to live shell and agent terminals, including Bento panes, and terminal history. Install the font in macOS and use its family name. An omitted or empty font_family uses system monospace. Twine checks that i and w have equal character widths, allowing Nerd Fonts whose icons are wider. An unavailable font or one that fails this check falls back to system monospace with a warning. font_size defaults to 13 points and accepts sizes from 6 through 72, including fractional sizes such as 13.5. appearance.color_scheme selects system, light, or dark appearance for all app windows.

A top-level import loads one or more complete TOML configuration files. Put it before any table headers in config.toml:

import = ["themes/silica_dark.toml", "fonts.toml"]

[terminal]
font_size = 14.0

[terminal.colors]
# Settings here override the imported files.
background = "#101820"
foreground = "#e5e1cf"
cursor = "#8fbe5c"
selection = "#34495e"

A single file can also use import = "themes/silica_dark.toml". Files merge in the order listed: later imports override earlier imports, then the importing file overrides them all. Tables merge recursively, so overriding terminal.font_size preserves an imported terminal.font_family. Individual terminal colors merge by name. Defaults fill omitted settings after merging. Imported files can contain any supported settings, including appearance and terminal fonts.

Imports accept absolute paths, ~/ paths, and paths relative to the file containing the import. Imported files can have their own top-level imports. Cycles are rejected, including cycles through symlinks; each import tree is limited to 64 levels and 256 documents. Invalid imported settings cause the complete config to fall back to defaults even if a later file overrides that setting. Diagnostics identify the original file, line, and key. Missing imported files are reported and never created.

Terminal colors normally come from themes/silica_dark.toml in dark mode and themes/silica_light.toml in light mode. Those files use the same config tables, so they can also be imported directly. A full palette import applies the same colors in both appearances. Partial imports and local overrides replace only supplied colors; omitted colors retain the corresponding default theme values.

For example, a theme file contains:

[terminal.colors]
background = "#101820"
foreground = "#e5e1cf"
cursor = "#8fbe5c"
selection = "#34495e"
black = "#1a2026"
red = "#ef4d4d"
green = "#8fbe5c"
yellow = "#d9bd54"
blue = "#4aa3e0"
magenta = "#dc63a0"
cyan = "#2dd6ab"
white = "#cac5b3"
brblack = "#7d8794"
brred = "#ff8383"
brgreen = "#a9e488"
bryellow = "#ecd77e"
brblue = "#7cd2f5"
brmagenta = "#f0a0d5"
brcyan = "#85f0d8"
brwhite = "#f7f4e8"

Colors must be #RRGGBB strings. Set ANSI colors individually with black, red, green, yellow, blue, magenta, cyan, and white. Bright variants use the br prefix: brblack through brwhite. Legacy ansi arrays remain readable; named colors override their corresponding slots. The same tables and keys work in config.toml and all imported files. Saving settings in Twine updates shell and agent terminals, Bento panes, saved output, and minimaps.

Omitted settings use defaults. Invalid TOML, invalid values, or file errors (including theme files) use the complete defaults; unknown keys are ignored with a warning. Diagnostics include the file, line, and key (or <document> when a syntax error has no identifiable key). They appear in macOS Console under the com.twineproject.Twine subsystem, without logging config values.

Terminal panes#

Use the two buttons at the top right, ⌘D to split right, or ⇧⌘D to split down. Each split starts a shell in the same folder; run any command or coding agent there. Up to four panes share the same Bento styling and draggable dividers as agent workflows. ⌘[ and ⌘] move keyboard focus. Each pane has a close button; ⌘W closes the focused pane, and closing the tab closes its panes. Pane layouts survive reopening. The Traces panel combines all panes in a tab into one set of tracks, and selecting an event focuses its owning pane.

Paste a clipboard screenshot with ⌘V, or drop images and files onto any terminal or agent pane. Clipboard images become private PNG files in the temporary directory; Twine inserts their quoted paths so the shell or harness can read them. File drops use their original paths. How much output remains in live scrollback depends on the harness's terminal display mode.

Terminal transcripts#

Every terminal and agent pane has a compact minimap at its right edge. Hover or focus the 14-point rail to expand it over the output; expansion does not change the terminal's columns. Click or drag the visible-region indicator to scroll. With the rail focused, use the arrow, Page Up/Down, Home, and End keys. Return to live resumes following the latest output. Each Bento pane keeps its own position.

Minimap points use the same step IDs, numbers, role colors, and selection as Traces. Selecting a point opens that step in Traces and scrolls the live terminal to its recorded position. Points are placed by terminal row; the Traces panel spaces steps by start order. Loading Older traces adds those steps to the map when their output is still available. Output without an available anchor remains scrollable without a guessed point. Historical output also has its own minimap.

Twine saves terminal output under ~/Library/Application Support/Twine/transcripts/. Terminal IDs remain unique across launches. Closing a terminal preserves output already accepted for recording. Reopening a folder restores recorded output and scrollback. Shells append a fresh prompt. Single agents resume their exact recorded harness session, retaining earlier output. Codex and Claude Code use session IDs; pi and OMP use session files. Antigravity and OpenCode support exact-ID resume but don't expose launch observers, so use Resume Session… to supply the conversation/session ID once. The same action is available for older tabs without a captured session. Twine never guesses the latest conversation. Cancelled or failed agents remain stopped. Saved output opens earlier invocations, including an idle shell with no trace step. Live views and ANSI replay retain up to 100,000 rows in memory; the raw transcript limits below apply independently. New workflows appear in Traces once their terminals are active.

Saved output is capped at 64 MiB per terminal and 512 MiB across all terminals. Older output expires when storage or metadata limits are reached. Expired output remains unavailable after reopening Twine.

Click an anchored event in trace details to select its workflow and agent and scroll the mounted terminal to that point. Return to live scrolls back to the latest output. If a point belongs to an earlier invocation or has left scrollback, Twine opens a read-only snapshot of the saved output instead. A restored workflow's Saved output menu opens earlier invocations. Saved output replays cursor movement and recorded terminal sizes; resizing the window only changes its viewport. It displays text without terminal colors or images. Events without an anchor keep their details without a jump action.

Saved output needs the earlier terminal output and its recorded sizes to display correctly. If either has expired, Twine shows Output no longer available.
